# Staging

`zikaron-staging` is published by CI on every merge to `main` (`.github/workflows/staging.yml`, which calls `deploy.yml`), against the test vault `guedesdiogo/zikaron-cofre-teste`, with synthetic data only. Nothing is published from a machine. After publishing, the deploy waits for `GET /health` to answer `{"status":"ok","environment":"staging","commit":"<sha>"}` with the published commit; production works the same way, by release ([production.md](production.md)).

## What has to exist

No value below goes into the repo or through a chat. The repo is public, and the log of every Actions step shows the variables unmasked: so everything that identifies the account, Access, the clients or the Worker's address is a **secret** of the `staging` environment, even when it is not a password. Only the test vault's name, which is already in the docs, is a variable.

| Where | Name | What it is |
|---|---|---|
| Secret of the `staging` environment | `CLOUDFLARE_API_TOKEN` | The CI token (below) |
| Secret | `CLOUDFLARE_ACCOUNT_ID` | Zikaron's account |
| Secret | `ZIKARON_GITHUB_APP_ID`, `ZIKARON_GITHUB_INSTALLATION_ID` | The `zikaron` GitHub App and its installation on the test vault |
| Secret | `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD` | The Access team and application |
| Secret | `ZIKARON_CLIENTS` | The JSON of the test clients ([api.md](api.md#the-deploy-configuration)) |
| Secret | `STAGING_URL` | The Worker's address, `https://zikaron-staging.<subdomain>.workers.dev`, exactly as wrangler prints it, with no trailing slash: that way the log masks it. If the token exists and this does not, the deploy fails before publishing, so the address does not go out unmasked |
| Secret | `E2E_NOAH_CLIENT_ID`, `E2E_ALAN_CLIENT_ID`, `E2E_OUTRO_CLIENT_ID` and the three `E2E_*_CLIENT_SECRET` | The three test tokens |
| Secret | `E2E_VAULT_TOKEN` | Fine-grained GitHub token, *Contents: Read and write* on the test vault only |
| Variable of the `staging` environment | `VAULT_REPOSITORY` | `guedesdiogo/zikaron-cofre-teste` |
| Worker secret | `GITHUB_APP_PRIVATE_KEY` | The App's key, in PKCS#8 |
| Worker secret | `GITHUB_WEBHOOK_SECRET` | Generated by `scripts/webhook-staging.sh` |

The environment secrets go in through `prumo-secrets aplicar`, which reads the names from `segredos.json` and asks for each value in a hidden prompt.

**The CI token** is a token of its own, with only *Account › Workers Scripts › Edit* and *Account › Account Settings › Read* on Zikaron's account, with no zone permission. Even so, it is valid for the whole account: the staging token could publish over the production Worker of the same account. It is an accepted risk while production and staging share the account; separating them takes another account.

The three test clients in `ZIKARON_CLIENTS`: `noah` (`exposed`, `ownerClaims`), `alan` (`privileged`) and `outro` (neither).

## Step by step

1. **CI token, account and address:** `prumo-secrets aplicar` writes `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` and `STAGING_URL` (the other names in the manifest can wait: the command asks for one at a time, and an empty Enter skips). The account's `workers.dev` subdomain shows up under *Workers & Pages*, in the dashboard.
2. **The `zikaron` GitHub App:**
   - create it at github.com/settings/apps/new, with the webhook off and the repository permissions *Contents: Read and write* and *Metadata: Read-only*;
   - install it only on the test vault, never on `kelpie-vault` (production has an App of its own, `docs/production.md`);
   - write the App ID and the installation ID as secrets (`prumo-secrets aplicar`).
3. **First deploy:** a merge to `main` publishes the Worker and checks `/health`. Without the App and Access, the vault stays off and every route besides `/health` and the webhook is refused: 401, or 500 without the clients' configuration.
4. **The App's key in the Worker,** in a terminal, in the repo's directory:

   ```bash
   openssl pkcs8 -topk8 -nocrypt -in <.pem file> | (cd apps/server && npx wrangler secret put GITHUB_APP_PRIVATE_KEY --env staging)
   ```

   Then delete the `.pem`.
5. **Access:**
   - turn on Access for the `workers.dev` of `zikaron-staging`;
   - create the service tokens `noah-teste`, `alan-teste` and `outro-teste` and a *Service Auth* policy with them;
   - create a *bypass* application for the `/webhooks/github` path and another for `/health`, which only states the environment and the commit. Without the `/health` one, the deploy publishes, but its check fails and the run goes red;
   - write `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `ZIKARON_CLIENTS` and the three Client IDs as secrets (`prumo-secrets aplicar`).
6. **Webhook:** `CLOUDFLARE_ACCOUNT_ID=<account> scripts/webhook-staging.sh guedesdiogo/zikaron-cofre-teste <STAGING_URL>`. The script generates the secret and writes it to the Worker and to the repository's webhook, without printing it.
7. **The run's secrets:** `prumo-secrets aplicar`.
8. **End-to-end run:** `gh workflow run e2e-staging.yml --ref main`.

## The end-to-end run

`scripts/e2e-staging.mjs` uses a new marker on every run and checks that:
- without a credential, the edge refuses;
- `noah` writes an outside note and something the owner said;
- a write with `context: cron` is refused;
- `alan` does not see the outside note through read, search, recall, pending or MCP, and neither does `outro`; `noah` does;
- `alan` sees what the owner said, through `noah`'s `ownerClaims`;
- removing the `review: pending` on GitHub shows the outside note to `alan`, through the webhook;
- a note written directly on GitHub reaches `alan`'s recall.

The test vault is disposable: the run's notes stay there, with the run's marker in the title.
